Project 1: BoaOps Readiness Engine

Type: Private MVP / Security readiness platform

Role: Founder, product owner, security architect, builder

Status: Active MVP

Demo: https://drive.google.com/file/d/1ESpZ6nhT5-fa-jemOp9fpvpo4IUulxjk/view

The demo is sanitized and intentionally excludes proprietary logic, customer data, sensitive implementation details, and private repository code.

Repository: Private due to proprietary product logic

Problem

Teams preparing for security reviews often have scattered evidence, incomplete documentation, unclear control narratives, and no clean way to determine whether they are ready for review.

The challenge is not always that the work has not been done. Often, the issue is that the work has not been organized into a defensible package that a reviewer, assessor, or security authority can evaluate efficiently.

What I Built

BoaOps is a readiness packaging engine that helps teams convert incomplete security and compliance inputs into structured, review-ready outputs.

Core capabilities include:

  • Structured security intake
  • Framework selection and mapping
  • Evidence intake workflows
  • Control mapping logic
  • Readiness scoring approach
  • AI-assisted compliance Q&A
  • Dynamic artifact generation
  • OSCAL-style structured output concepts
  • Security-focused data handling patterns

Example Outputs

BoaOps is designed to support or generate:

  • System Security Plan
  • Plan of Action and Milestones
  • Security Assessment Plan
  • Security Assessment Report
  • Risk Assessment Report
  • Concept of Operations
  • Configuration Management Plan
  • Incident Response Plan
  • Continuous Monitoring documentation
  • OSCAL-style JSON outputs

Tech Stack / Concepts

  • AWS-hosted demo environment
  • Document generation
  • Evidence intake workflows
  • Compliance mapping logic
  • AI assistant workflows

Type: Private MVP / RMF and ATO automation workflow

Role: Security automation builder

Repository: Private

Problem

ATO and RMF documentation is often slow, repetitive, and inconsistent. Teams commonly rely on static templates that do not adapt well to system type, impact level, cloud environment, deployment model, or data classification.

This creates rework, inconsistent narratives, and weak linkage between system context and required documentation.

What I Built

I built an ATO automation workflow that dynamically generates security documentation based on structured system inputs.

The tool uses inputs such as:

  • System type
  • Cloud environment
  • Deployment model
  • Impact level
  • Data classification
  • Framework selection
  • Security control focus areas
  • Compliance needs

Example Outputs

The workflow supports generation of:

  • ATO Summary
  • System Security Plan
  • Plan of Action and Milestones
  • Concept of Operations
  • Configuration Management Plan

Project 3: DevSecOps Tooling Assessment

Type: Client-facing security assessment
Role: Principal DevSecOps / security advisor
Status: Delivered engagement

Problem

Organizations often adopt multiple AppSec and DevSecOps tools without a clear operating model for how findings move from discovery to prioritization, remediation, validation, and reporting.

Common issues include:

  • Tool overlap
  • Inconsistent vulnerability workflows
  • Weak developer handoff
  • Unclear remediation ownership
  • Limited executive visibility
  • Poor alignment between AppSec, DevOps, and risk teams

Scope

The assessment considered tools and workflows such as:

  • GitHub
  • Azure DevOps
  • Veracode
  • Snyk
  • StackHawk
  • Vulnerability management processes
  • Secure SDLC workflows
  • Developer remediation paths
  • Security reporting needs

What I Delivered

  • Current-state tooling review
  • Gap assessment
  • Future-state recommendations
  • Phased remediation roadmap
  • Tooling transition considerations
  • Security workflow improvements
  • Executive-facing implementation plan

Outcome

The work helped define a clearer path for AppSec modernization, vulnerability management alignment, developer adoption, and reduced tooling friction across development teams.
